# Logs de diagnóstico do servidor

Em desenvolvimento, o terminal mostra mensagens e campos legíveis em inglês no formato `[horário] [nível] [request_id] recurso · etapa · fatos`. O `request_id` aparece apenas com o primeiro bloco do UUID no terminal; o JSON preserva o valor completo. `INFO` é verde, `WARN` amarelo e `ERROR` vermelho quando o terminal aceita ANSI. Cada procedure tRPC informa operação, recurso, usuário, duração e resultado. Fluxos principais acrescentam marcos de negócio, como período letivo localizado, turmas elegíveis e arquivo encaminhado à fila. Checkpoints genéricos bem-sucedidos não são emitidos; o Next também não repete as requisições HTTP. `LOG_LEVEL=debug` mostra diagnósticos adicionais, e `LOG_FORMAT=json` usa a saída estruturada também localmente.

Em staging e produção, a saída permanece JSON, um evento por linha. `timestamp` usa UTC; `level`, `service_name`, `request_id`, `user_id`, `resource`, `operation`, `duration_ms` e `status` permitem filtrar o fluxo. Erros críticos incluem `exception` com o stack completo em uma única string JSON e `diagnostic_state` com estado explicitamente selecionado. O terminal de desenvolvimento pode mostrar as linhas do stack separadamente; a nuvem nunca recebe linhas soltas.

Não registre entradas tRPC, cabeçalhos, cookies, tokens, emails, nomes de alunos, termos de busca ou payloads de jobs. Eventos de processo podem incluir apenas contagens e indicadores booleanos revisados no código. Use o `request_id` para correlacionar eventos de uma chamada. Os jobs do worker usam `job_id` próprio; não herdam o ID HTTP.
